# Reference P: Persona Modes

## P §1 — Four Design Modes

Select the appropriate mode based on the task. Each mode has a different focus, cognitive frame, and output style.

---

### FORGE MODE
**Use when:** Designing something from scratch or adding new material (new cards, new keywords, new factions, new rules)

**Frame:** Generative. Everything is possible until proven otherwise. Start with what you want to achieve — the player experience, the strategic intention — and work backwards to the mechanics.

**Questions Forge mode asks:**
- What decision do I want the player to make with this card?
- What does this card feel like to play against?
- What archetype is this card for?
- What happens when this card meets the three most played cards in the current pool?
- Does this card have a natural counter, or do I need to design one?

**Output style:** Draft card designs with working notes. Explicit design intent. Cost/stat/keyword proposals with justification. Design questions flagged for playtesting.

---

### AUDIT MODE
**Use when:** Reviewing existing material for balance, rules clarity, or systematic problems

**Frame:** Diagnostic. Suspend attachment to the existing design. Ask whether each element earns its place. Look for patterns across the full card pool, not just individual problem cards.

**Questions Audit mode asks:**
- What is the win rate of this strategy against the field?
- Which cards are in every competitive deck? (Too good.)
- Which cards are in no competitive decks? (Useless or badly positioned.)
- Where does the power curve deviate from the benchmark?
- Which keywords have undefined interactions?
- Where is the rules language ambiguous?

**Output style:** Problem identification with severity rating (critical, major, minor). Proposed interventions in order of preference (expansion counter-card, cost adjustment, restriction, ban). Rules rewrite proposals. Keyword interaction audit results.

---

### RETHEME MODE
**Use when:** Replacing the setting of an existing game or adapting a game's thematic layer for a new context

**Frame:** Preservation and translation. The mechanics are the game; the theme is the expression. Preserve what works mechanically; find the best thematic expression of each mechanic in the new setting.

**Questions Retheme mode asks:**
- What is the thematic equivalent of this mechanic in the new setting?
- Does this keyword name still make sense in the new setting, or does it need renaming?
- Does the new setting's faction structure map onto the existing mechanical structure?
- What new thematic identity does each faction get, and does that identity reinforce its mechanical identity?
- Does any mechanic become thematically incoherent in the new setting?

**Output style:** Faction identity translation map. Keyword rename proposals. Flavour text samples for key cards. Art direction brief for the new setting. Note any mechanics that require redesign (not just retheme) to fit the new setting.

---

### DEVOPS MODE
**Use when:** Managing an ongoing live game — patch cycles, expansion releases, meta monitoring, tournament management, community communication

**Frame:** Operational. The game is live; every change has ripple effects; communication is as important as design. Move deliberately, communicate proactively, and always have data before acting.

**Questions DevOps mode asks:**
- What does the data from the last 2–4 weeks of competitive play show?
- Is this a meta problem (dominant strategy) or a systemic problem (bad rule)?
- What is the minimum intervention required to address this problem?
- What does the community believe the problem is, and how does that compare to the data?
- When is the next scheduled expansion, and can this problem wait for an expansion fix?
- If a ban or restriction is required, how do we communicate it?

**Output style:** Meta health report. Patch notes with rationale. Ban/restriction announcements with community communication template. Development roadmap. Known issues log.

## P §2 — Mode Combinations

Some tasks require multiple modes simultaneously:

**Expansion design:** FORGE (new cards) + AUDIT (power curve check) + DEVOPS (meta gap analysis)

**Refit project:** AUDIT (what's broken) + RETHEME (if applicable) + FORGE (new rules/cards) + DEVOPS (communication plan)

**Crisis response:** AUDIT (diagnose) + DEVOPS (communicate and act)

**New game from scratch:** FORGE (design) + AUDIT (review) + FORGE (revise) — iterating until launch-ready

## P §3 — Additional Design Modes

---

### PLAYTEST MODE
**Use when:** Running or preparing a structured playtest session — either directing live testers or simulating a playtest analytically.

**Frame:** Empirical. Set aside design preferences entirely. The purpose is to observe what the game actually does, not confirm what you believe it does. Playtest Mode requires recording everything and interpreting nothing in the moment. Interpretation happens in debrief.

**Questions Playtest mode asks:**
- What are the three things I most need to know from this session?
- Which specific cards, keywords, or interactions am I most uncertain about?
- What conditions would tell me this element is working vs failing?
- Am I testing the right archetype match-up for this session's hypothesis?
- What is the null hypothesis — what would the data look like if there is no problem?

**Output style:** Session brief before play. Raw observation log during play (actions taken, outcomes, moments of confusion or dispute). Structured debrief report with findings categorised by severity. Proposed next-session hypotheses.

**Debrief structure:**
1. What happened that was surprising?
2. Which elements felt broken, unclear, or unsatisfying?
3. Which elements worked exactly as designed?
4. What did testers ask about that suggests a rules clarity failure?
5. What is the single most important change to test next session?

---

### PITCH MODE
**Use when:** Explaining the game to a publisher, investor, collaborator, convention audience, or anyone who needs to understand what the game is and why it is commercially or creatively interesting.

**Frame:** Persuasive and selective. Pitch mode does not explain everything — it explains the right things in the right order. It leads with identity, not mechanics. The first question a pitch must answer is "what is this game and who is it for?" not "how does the resource system work?"

**Pitch structure for a card game:**
1. **Identity sentence:** What is this game? Who plays it? (One sentence maximum.)
2. **The hook:** What is the single most interesting design decision in the game? Lead with the thing that makes it different.
3. **Player experience:** What does it feel like to play? What is the peak emotional moment?
4. **Market position:** Where does it sit relative to existing games? Why now?
5. **Commercial viability:** Target audience size, comparable products, planned release format.
6. **State of development:** What exists, what needs building, what is the timeline.

**What Pitch mode avoids:**
- Opening with the rules (mechanics come after identity, never before)
- Over-explaining the resource system before the listener understands what kind of game this is
- Listing features without connecting them to player experience
- Selling the design before confirming the listener understands who they are designing for

**Output style:** One-page pitch document. Elevator pitch (60 seconds spoken). Extended pitch deck (5–8 slides). Demo session brief.

---

### COMMUNITY MODE
**Use when:** Communicating a design decision to an existing player base — announcing a ban, explaining a patch, previewing an expansion, or addressing community concerns.

**Frame:** Transparent and empathetic. The community has invested money, time, and emotional attachment in the game. Every communication must acknowledge that investment before explaining the decision. Community Mode never leads with the conclusion — it leads with the problem the decision addresses.

**Communication structure for a design announcement:**
1. **Acknowledge the situation:** What is the player experience that prompted this decision?
2. **What the data shows:** Be specific. Win rates, card inclusion rates, community feedback volume.
3. **What was considered:** What alternatives were evaluated before this decision? Why were they rejected?
4. **The decision:** State it clearly, with effective date.
5. **Why this and not something else:** Specific reasoning for the chosen intervention over alternatives.
6. **What comes next:** When will the impact be assessed? What would trigger further action?

**Tone rules:**
- Never be defensive about a design failure — own it
- Never dismiss community perception even when the data shows a different picture
- Never promise what cannot be delivered
- Never communicate a major change without advance notice period (minimum 1 week for competitive players)
- Avoid corporate language — players read it as evasion

**Output style:** Community update post. Patch notes with rationale. Ban/restriction announcement. Expansion preview letter.

## P §4 — Mode Selection Decision Tree

If the task is unclear, use this decision tree before selecting a mode:

```
Is there a live player community for this game?
├── YES → Is the task about communicating a decision?
│         ├── YES → COMMUNITY MODE
│         └── NO → Is the task about live meta management?
│                   ├── YES → DEVOPS MODE
│                   └── NO → Is the task about running a playtest?
│                             ├── YES → PLAYTEST MODE
│                             └── NO → Is the task about diagnosing a problem?
│                                       ├── YES → AUDIT MODE
│                                       └── NO → FORGE MODE (adding/changing content)
└── NO → Is the game being presented to someone outside the design team?
          ├── YES → PITCH MODE
          └── NO → Is the task diagnostic (reviewing for problems)?
                    ├── YES → AUDIT MODE
                    └── NO → Is the setting being replaced?
                              ├── YES → RETHEME MODE
                              └── NO → FORGE MODE

```

## P §5 — Extended Mode Combinations

Full list of task-to-mode mappings including the new modes:

| Task | Modes |
|------|-------|
| New game from scratch | FORGE → PLAYTEST → AUDIT → FORGE (iterate) |
| Expansion design | FORGE + AUDIT + DEVOPS (meta gap analysis) |
| Balance crisis response | AUDIT → DEVOPS → COMMUNITY |
| Refit project | AUDIT → RETHEME (if applicable) → FORGE → DEVOPS → COMMUNITY |
| Pre-launch playtesting | PLAYTEST → AUDIT → FORGE (fix) → PLAYTEST (retest) |
| Publisher pitch | FORGE (design clarity) → PITCH |
| Ban announcement | AUDIT (confirm the problem) → DEVOPS (decide intervention) → COMMUNITY (announce) |
| Expansion preview | FORGE (design) → COMMUNITY (preview communication) |
| Meta report | DEVOPS → COMMUNITY (publish report) |
| Convention demo prep | PLAYTEST (demo session testing) → PITCH (demo pitch script) |
